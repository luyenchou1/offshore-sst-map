# GotOne Offshore SST Analyzer — Project Context

## What This Is
**GotOne Labs** (labs.gotoneapp.com): free, experimental tools for saltwater anglers from [gotoneapp.com](https://www.gotoneapp.com), one Dash 4.0 app. The home page has a tile per tool; the tools are the **Offshore SST** map (`/sst`) and **Currents** (`/currents`). The SST map shows daily sea-surface temperatures for the Cape May, NJ to Portland, ME offshore corridor. Users pick any 7-day date window (back to June 2002) and animate through the week's SST evolution to spot fishing-relevant trends (warm eddies, cold upwelling, thermoclines).

## Architecture

### SST Data Sourcing — cache first, seeded off-Render as insurance

**History:** from June 2026 NOAA CoastWatch ERDDAP blocked Render's datacenter IP at the network layer (`Network is unreachable`, `Connection reset by peer`, connect timeouts; `coastwatch.noaa.gov` additionally tarpits with `ReadTimeout` from every IP), so cache misses on Render hung the full 90s and showed the red "SST fetch timed out after 90s" error. **As of 2026-10-10 the block is lifted** — Render fetched an uncached Oct 8 window live in ~10 s. **On 2026-10-16 it was back**: from Render every request to coastwatch.pfeg waits out the connect timeout and then says `[Errno 101] Network is unreachable` (see ERDDAP Behavior), and together with the fishing-activity proxy that took the whole server down (Critical Lessons, Incident 2026-10-16). The off-Render seeding is what serves cache misses while it lasts.

- **Render (production)** serves from its disk cache first; on a miss it asks ERDDAP via `get_sst_multiday()`, unless NOAA failed to connect in the last minute: then it answers at once with the honest message and the nearest saved weeks, and queues the week for the seeder.
- **Off-Render seeder**: a daily GitHub Action (`.github/workflows/seed-sst-cache.yml`) runs `tools/sync_cache.py`, which fetches recent 7-day windows from ERDDAP and POSTs weekly files (`<end>_week.json.gz`, see SST data, cache and engine) to `POST /api/cache/upload` (auth: `CACHE_UPLOAD_TOKEN` env var + GitHub repo secret). Seeds the 10 end dates ending on MUR's newest day, twice daily, plus weeks readers asked for that NOAA couldn't send (see SST fetch below), plus up to 24 weeks a run that the app still has only in the format from before sprint 2 (the backfill). Uploads retry on transient Render 502s. **GitHub silently disabled this job for inactivity on 2026-08-30**; `.github/workflows/keepalive.yml` now prevents that (see Lessons).
- **localhost (dev)** fetches ERDDAP live, exactly as the Data Flow below describes.

### SST fetch: known datasets, one time budget, OISST fallback, payload meta (Oct 2026)
- **Sources** (`config.json` "erddap"; defaults in `data/erddap.DEFAULT_SOURCES`): MUR `jplMURSST41` (`analysed_sst`, stamped 09:00Z) on coastwatch.pfeg. OISST v2.1 `ncdcOisst21Agg_LonPM180` (final, 1981-09-01 to about two weeks ago), then `ncdcOisst21NrtAgg_LonPM180` (near-real-time, 2020-05-04 to yesterday): `sst` with a `[(0.0)]` zlev, stamped 12:00Z, 0.25 degree. No dataset search at request time (the search pages 403/404 from cloud IPs). Dropped: upwell.pfeg (it 302s to coastwatch.pfeg, same backend) and coastwatch.noaa.gov (no MUR; 404, tarpits). None of polarwatch, cwcgom, apdrc, pacioos, ioos, ncei or marine.ie serves `jplMURSST41` (checked Oct 2026).
- **Budget**: `get_sst_multiday()` runs every request against one `Deadline` (`budget_s`, 22 s). Connect 3 s / read 8 s timeouts are capped by the time left, 429/5xx/network errors are retried after about 1 s and 2.5 s only while time allows, and days go 3 at a time, newest first (`concurrency`). It returns at the deadline even if requests are still running (they end on their own at the deadline too). The callback adds under a second (land mask cached per grid, PNGs), so a miss answers in about 23 s at worst (once after a restart, up to 5 s more if the land mask is still downloading).
- **Outside calls can't hang a thread** (`data/outbound.py`, since the Oct 16 incident): every NOAA request runs on the NOAA upstream's own threads (at most `NOAA_MAX_CALLS`, 10, in flight; a full pool answers "busy", which is retried) and the caller waits only until its deadline. The body is read in pieces (`read1`) with the deadline checked after each and the socket timeout capped by the time left: requests' `timeout` is per read, so before this a server sending a byte every few seconds held the thread for hours (`iter_content(64 KiB)` waits for a whole chunk).
- **Fail fast when NOAA is unreachable**: after one connect failure (errno 101, refused, no DNS, connect timeout) the NOAA circuit breaker refuses requests for 60 s, then lets one through to probe (log: "NOAA ERDDAP (...) is failing ... not asking it for 60s", then "answers again"). In that minute a fetch fails at once (kind `unreachable`, never retried; reason `network`), MUR days stop at the first such failure and OISST (same server) isn't tried. At most `SST_NOAA_READERS` (4) request threads wait on NOAA at once (fetching, or waiting for another visitor's fetch of the same week); the next reader gets the same honest answer at once. Read timeouts don't open the breaker (a slow MUR still leaves time for OISST).
- **Newest day**: `latest_mur_date()` reads ERDDAP `time[last]` (a tiny csv), cached for an hour; a failed lookup keeps the last good answer and isn't retried for 5 minutes. One lookup per dataset is in flight at a time (other callers wait for it, at most their own limit). The date picker's default and max and the fetch callback use it without waiting (`block=False` refreshes in the background; the lookup starts at import), the automatic first load uses it once known, and a request past it is clamped inside the fetch (`week_match: "newest"`).
- **Exact time stamps**: a day is requested at its stamp (`[(2026-10-15T09:00:00Z)]`), a range stamp to stamp, and the date that comes back is checked (ERDDAP snaps a single value to the nearest day, so a gap day comes back as its neighbour). ERDDAP rejects a stop past the axis maximum, so the old `T00:00:00Z` to `T23:59:59Z` day range 404'd on the newest day every time: that is why the page could never show it.
- **Fallback**: OISST only when MUR sent no day before the last 5 s of the budget (kept for OISST); one request per OISST dataset for the whole week (~20 KB). A partial MUR week (some days still 503 at the deadline) is served and says which days are missing. The orient/mask/convert pipeline takes both grids: masks and overlay bounds use cell edges (`geo.grid_edges`, half a cell beyond the first and last centres: 500 m for MUR, 14 km for OISST).
- **Failure**: `SSTUnavailable(reason)`, reason busy, blocked, network, no_data or dead. The sidebar says why in plain words ("network": "We can't reach NOAA's data server right now, so ... didn't load."; "busy": "NOAA's data server is busy and didn't send ... in time."), offers the 3 nearest saved weeks as buttons (`{"type": "saved-week", "index": ISO}`, from `cache.nearest_saved()`, the file index), and opens the drawer on phones so it's seen.
- **Saved weeks** (`_load_week` in app.py: first everything that needs no NOAA (`_week_without_noaa`: a copy that needn't be refreshed, the closest saved week, a week that failed in the last minute), then a NOAA reader slot, then a per-week lock so two visitors on one uncached week fetch it once (the second waits at most one budget, then re-checks); a week NOAA failed to send isn't asked for again for a minute, counted from the failure, not from the last time someone asked): an exact copy that is final is served; weeks ending within 10 days of the newest day are always fetched; older weeks take the closest saved week within 3 days first (`"closest_saved"`). A copy due a refresh (`sstmeta.refresh_due`: fetched while days were preliminary, after 12 h; inside MUR's 7-day revision window, 24 h; OISST or incomplete, 6 h) is refetched with a 10 s budget, at most every 30 minutes, and served as is if that fails (`"older_copy"`). A fetch never replaces a better copy (MUR beats OISST, then more days).
- **Seeder queue**: a week NOAA couldn't send (failed, partial or OISST) goes on `<cache>/sst/wanted.json` (at most 30). `GET /api/cache/wanted` (X-Upload-Token, like the upload) lists it, `tools/sync_cache.py` fetches up to `--max-wanted` each run, and uploading a complete MUR week takes it off. The page then says "We'll have this week ready within a day".
- **Seeder**: the 10 end dates ending on the newest MUR day (today - 1 if the lookup fails), twice daily (11:00 and 21:00 UTC), MUR only, whole weeks only, 150 s per week, 2 days at a time. `/api/precache` (token-locked) uses the same MUR-only rules with a 100 s budget.
- **Payload meta** (`data/sstmeta.py`; in the `sst-store` data and every cache entry): `source` "MUR" or "OISST", `source_label`, `resolution_km` 1 or 25, `dataset_id`, `server`, `days` (ISO dates served), `requested_end`, `served_end`, `latest_available`, `built_at` (UTC, when fetched from NOAA), `from_cache`; extras `missing_days`, `complete`, `preliminary_days` (under 4 days old when fetched), `week_match` ("exact", "newest", "closest_saved", "older_copy"), `queued`. Old entries without meta load with it filled in (source from dataset_id, days from dates, built_at from the file time). The date box is set to the week served.
- **Tests**: `OBJC_DISABLE_INITIALIZE_FORK_SAFETY=YES .venv/bin/python tools/test_sst_fetch.py` (fake ERDDAP: 503 then success, 403, dead dataset, timeouts, gap days, the newest day, OISST final/NRT split, partial weeks, honest failure, refresh rules, GFW per-request range, layers, the wanted queue); `tools/test_sst_hang.py` (real sockets: drip, tarpit, refused, errno 101, no DNS, IPv4 dropped; 30 readers at once, a slow NOAA, slow or unreachable GFW, the land mask, the diagnostics); `tools/load_sst_outage.py` (gunicorn as production under tools/netsim, 50 concurrent mixed requests, every answer within 30 s).
- **Without the land mask** (still downloading after `geo.LAND_WAIT_S`, 5 s in the app and waited once per load, or its download failed) a fetched week is shown but not saved (`w["save"]`); precache waits up to 60 s for it and never saves a week without it.

### SST data, cache and engine (sprint 2, Oct 2026)
The browser draws the SST itself (review E1): the server only sends one compact binary per week, and
`assets/sstengine.js` (`window.SSTEngine`) colors it, draws it in place, reads values and animates the days.
- **Coverage**: 37.8 to 44.0 N, 76.0 to 64.8 W (past Oceanographer Canyon, south to the Gulf Stream). `config.json`
  `aoi_polygon_lonlat` is that box and `coverage_id` names it (`box-2026-10`); land is masked with Natural Earth 10m
  (`data/geo`). MUR's 0.01 degree grid is 1121 x 621 cells, 30% land; one day is 1.2 MB on the wire (1.3 to 1.6 s).
  The first view (`assets/sst.js` AREA) and the fishing-activity tile bounds (`layout/mapview.AOI_TILE_BOUNDS`) use it.
- **0.1 F**: ERDDAP values are kept to 0.1 F (`data/convert.to_fahrenheit`; whole degrees before, review R4).
- **One file per week** (`data/sstgrid.py`, `"grid_format": 1`): `SST_CACHE_DIR/sst/weeks/<end>_week.json.gz`, gzip
  JSON with dates, bounds (cell edges), the Auto range (`vmin`/`vmax`), `precision`, `coverage`, `meta` and `grid` =
  base64 of the week's gzip GOSST1 bytes. No adaptive/locked pair any more: the color scale is the browser's.
  GOSST1 (layout in the module doc): a 64-byte header, one water/land mask for the week, and per day the codes
  (0.1 F steps from 28 F) as left-neighbour residuals in zigzag bytes, with escapes for big jumps. Built in one place,
  `sstgrid.entry_from_fetch()`, by the reader fetch, `/api/precache` and the seeder alike.
- **Sizes** (week of Oct 9 to 15, 2026, real MUR over the box): 588 KB at gzip -9 (the seeder; ~3.6 s to encode),
  641 KB at -6 (anything built on Render; 0.3 s). Plain gzip of the uint16 codes was 1002 KB; byte planes 855 to
  939 KB; other predictors within 4% (the 0.1 F quantization noise is the floor). The JSON file is ~5 KB more.
- **The week's bytes**: `GET /api/sst/week/<end>.bin` sends the gzip bytes as they are with `Content-Encoding: gzip`
  (every browser inflates them natively), ETag/304, `max-age` 1 h; the page's URL carries `?v=<built_at>`, so a
  rebuilt week is fetched again. From memory, the weekly file, or an old entry converted on the fly: never NOAA, no
  lock, 404 when the week isn't saved (the page always loads a week through Load week first).
- **sst-store** (`sstgrid.store_payload`): `dates`, `bounds`, `vmin`/`vmax` (Auto), `res_km`, `server`,
  `dataset_id`, `meta`, `data_key` (`"<end>_week"`), `grid` {`url`, `bytes`, `nx`, `ny`, `precision` (0.1, or 1 for an
  old week), `coverage`, `format`}. No pictures: about 2 KB (it was 190 KB of PNG frames).
- **Old entries** (`SST_CACHE_DIR/sst/<end>_<adaptive|locked>.json.gz`, saved before sprint 2: the old corridor
  38.8 to 43.8 N, 74.96 to 68.8 W, whole degrees, any of the old encodings): either variant loads, is converted to
  GOSST1 on its own grid each time it's served (~0.2 s; the bytes are kept in memory, `_blob_cache`), is drawn on its
  own bounds, and is never rewritten: the seeder replaces the week (backfill below). Code from before sprint 2 only
  globs `sst/*.json.gz`, so it never sees `sst/weeks/` and a rollback keeps serving the old files.
- **What the reader sees during the switch**: weeks saved before the deploy show whole degrees over the old corridor
  until the seeder rebuilds them; weeks fetched or seeded after it have tenths and the larger area. The first seed run
  after the deploy rebuilds the 10 newest weeks; older saved weeks follow newest first, about 48 a day.
- **SSTEngine API** (the seam with assets/sstlook.js, lane V): `attach(map)` (the engine also attaches itself to the
  `sst-map` map; idempotent), `setWeek(payload)` (the sst-store data; fetches `grid.url`), `setDay(i)` (300 ms
  crossfade unless the reader prefers reduced motion), `setPalette("spectrum" | "classic" | "cvd")` (design-notes
  stops; the old 11 colors; cividis), `setRange({mode: "auto"})` (5th to 95th percentile of all water in the coverage
  over the week, rounded out to whole degrees, at least 8 F: the same integer rule as `sstgrid.auto_range`, so it
  equals the server's `vmin`/`vmax`) or `{mode: "fixed", min, max}`, `fitToView()` (5th to 95th of the water on screen
  over the week, whole degrees, at least 3 F; sets a fixed range, returns `{min, max}`), `setOptions({stepped,
  isotherms, breaks, opacity})` ("haze" is ignored), `valueAt(lat, lon)` -> `{f, day, date, estimate: null}` or null,
  `weekValuesAt(lat, lon)`, `nearShore(lat, lon)` (true where the coast fill colors water the week has no value for;
  the tap card then says "No satellite reading this close to shore"), `histogram()` -> `{min, max, step, bins, below, above, total}` (the week's water, all days,
  bins of 0.5 F up to a 24 F range, else 1 F), `on("ready" | "change" | "day" | "error", fn)` (returns off). Extras:
  `getRange()` -> `{mode, min, max}`, `colorFor(f)` -> `[r, g, b]` (prints as `rgb(...)`), `state()`, `palettes`,
  `_stats` (timings). "ready" fires each time a week's data is in (also when the same week is delivered again).
- **Drawing**: an `L.Canvas` renderer in `sst-pane` (z 410, pointer-events none), so Leaflet moves and scales it while
  panning and zooming. Per day, a canvas the size of the grid colored through a 65536-entry lookup table (palette x
  range x stepped), blended toward white by the break strength; drawn in strips of 16 grid rows, each placed by Web
  Mercator at its cell edges (under 0.1 px of error at zoom 12; strips snapped to whole device pixels so they neither
  overlap nor gap). Isotherms (every 1 F, 0.9 px at 95% on even degrees, 0.5 px at 60% on odd, tonal colors, loops
  under 26 px dropped, sparse labels on even degrees: at most 2 per level 420 px apart, 1 per level 300 px apart on
  phone-sized maps, straight stretches in water only) and breaks (gradient on the field blurred 1 cell, F per km,
  zeroed within 3 cells of land; highlight from 0.27 F/km = 0.5 F per nm, full at 0.54 F/km = 1 F per nm, up to 62%
  toward white) are computed once per day in a Web Worker (blob URL; the main thread a day at a time if workers are
  blocked), the day on the map first. Whole-degree weeks are blurred more (3 and 2.5 cells) so their terraces don't
  read as fronts. Each day is rendered once per view into a canvas of its own (colors, isotherms and labels, the
  coastline; `compLayer`, at most 3, 2 on a big retina screen), and the next and previous days are prepared when
  the browser is idle (one per idle slot), so a frame, also mid-crossfade, composites one or two images.
- **The coast** (Oct 17, 2026; `docs/coast-progress.md`): (1) *fill under the coast*: once the coastline is in, the
  week's masked cells within 3.5 km of water (3 MUR cells; whole cells only, so none on OISST) get values ring by ring (8-connected), each
  the mean of its neighbours in earlier rings (`buildPlan` once per week, ~10 ms on a slow phone; `dispCodes` per day,
  ~3 ms). Drawing only: `S.week.days` stays as decoded, so readouts, the histogram, Fit to view, isotherms and breaks
  never see a filled cell (the worker gets the decoded codes; isotherms are cut 2 cells from the week's mask as
  before). On the week ending Oct 14, 2026, 3 cells reach 94.5% of the OSM water MUR leaves out (4: 96.3%); what
  isn't reached is up rivers. (2) *the coastline* (`assets/sstland.js`, OSM land polygons from `tools/build_land.py`):
  drawn into each day's canvas after the colors and isotherms: the land is cleared ("destination-out", one path for
  the pieces in view, nonzero; pieces overlap ~20 m so cuts never show), so the SST stops at a smooth antialiased
  coastline and the basemap shows on land as it is; islets under 1 km2 are painted land color over the SST instead
  ("source-atop": Esri leaves many out, e.g. Casco Bay); from zoom 11 a 2 px rim of land color is stroked under what's
  left ("destination-over", from the level below, widened by its tolerance) to cover slivers where Esri's coast and
  OSM's differ (Bellport Bay, Montauk's north shore at zoom 12). Isotherm labels also avoid OSM land (land cover per
  cell, rasterized from level 0 when idle). Without the coastline (its fetch failed) the map is drawn as before: no
  fill, no clearing. (3) *interpolation*: from a cell 3 CSS px wide (MUR zoom 9; the 0.02 degree test grid zoom 8;
  OISST zoom 5) the visible map is drawn bilinearly between cell centres (`interpImage`, per view and day, masked
  neighbours left out by weight, drawn where they weigh 0.25 or more with a 1 px antialiased edge, breaks blended the
  same way; output about 10 ms of work on the device, self-tuned from its measured ns per pixel, up to 1.5M pixels;
  the padding around the view is drawn as cells, seen only mid-pan). In Stepped mode the interpolated bands come from
  the field smoothed as the isotherms are (Gaussian sigma 1.3 cells, 3.0 for whole-degree weeks, normalized over
  cells with a value, computed over the cells in view), so a band's edge is the temperature line instead of 0.1 F
  noise traced cell by cell where the water is nearly even; smooth colors use the cells as they are.
- **Frame times** (`node tools/perf_sstengine.mjs`, phone 390x664 @2x, CPU slowed 4x in CDP): decode a week 63 ms,
  histogram 54 ms (once per week); a palette / range / stepped change 5 ms (20 back to back: 4.7 ms each); a day

  and breaks on; isotherms + breaks for a day 160 to 270 ms in the worker; a redraw with isotherms under 3 ms of

  Coast (Oct 17, `--only coast`, same profile; headless Chrome rasters canvases in software, so drawing costs are
  pessimistic next to a phone's GPU): crossfade frame gaps median 16.7 ms (was 33 to 50, 90th percentile 50 to

  with Breaks on at zoom 11, 97 vs 90), at zoom 7 the same as before (~160 ms); interpolation ~10 ms per view (Stepped

  file prepared in under 6 ms; the fill plan 10 ms once per week, 2 to 3 ms per day. Laptop (1440x900 @2x, no
  throttle): pan end 48 to 62 ms (39 without), interpolation 7 to 10 ms at about CSS-pixel resolution.
- **Readouts** (review R1): the tap card (reading, spot, a point in The Dump) is drawn by `assets/sst.js`
  (`SST.selection`) from `SSTEngine.weekValuesAt()`: tenths ("71.3 °F"), no server trip on a tap or a day change. A tap
  on the card's own marker closes it (an identical second tap gives Dash the same clickData, which wouldn't refire the
  tap callback). The measure line and panel stay server-side (`render_selection`, true + magnetic course), with the
  ends' temperatures from the week's arrays decoded server-side (`_get_raw_data`, 0.1 F, float32, two weeks in memory).
- **No cloud layer** (review D3, deferred): MUR's `analysis_error` was the planned source of a haze where the value
  is an estimate, but over the box it is 0.36 to 0.40 °C on every date checked (12 dates, 2005 to 2026; 4 or 5
  distinct values, never above 0.40), so it can't tell a cloudy week from a clear one, and the haze was dropped
  (Luyen, Oct 16, 2026). A real signal would need its own fetch (per-pixel L3 infrared observation counts, for
  instance); GOSST1's header keeps bytes 40 to 63 reserved for it.
- **Retention** (what is kept, refreshed, or lives in memory):
  - *Final and kept*: a week fetched 7 or more days after its last day (MUR's revision window has passed) is never
    fetched again.
  - *Refreshed* (`sstmeta.refresh_due`; the saved copy is served if the refetch fails, which on Render is at once while
    NOAA is unreachable): a week with preliminary days (fetched under 4 days after its last day) after 12 h; a week
    inside MUR's 7-day revision window after 24 h; an OISST or incomplete week (a day NOAA didn't send in time): MUR is
    tried again after 6 h, and the week goes on the seeder's list. The seeder rebuilds the 10 newest weeks twice a day.
  - *Disk* (`data/cache.evict`): the SST files may use 70% of their disk (`SST_CACHE_MAX_MB` overrides); past that,
    old entries whose week has a weekly file go first, then the least recently viewed (serving a week sets its file's
    access time, at most hourly; the modification time is kept). A small dedicated disk (64 GB or less, like Render's
    1 GB) also keeps 5% of itself free. A file viewed or written in the last 10 minutes is never evicted; `MAX_ENTRIES`
    (4000 files) is only a backstop. On Render's 1 GB disk: 700 MB, about 1100 weekly files. An evicted week only comes
    back through the seeder (Render can't reach NOAA). The startup log line `SST cache at startup: {...}`,
    `/api/debug/threads` and `/api/cache/weeks` give files, MB, the disk and the budget: size the cap from those.
  - *Memory only* (gone after every deploy or restart): the GFW tiles (300) and generate-png styles (32 ranges), the
    newest-day lookup (1 h; a failure 5 min), the decoded weeks for the measure panel (2), the converted old weeks'
    bytes (4), the per-week failure and refresh timers. The seeder's wanted list is on disk (`sst/wanted.json`).
- **Backfill** (`tools/sync_cache.py --backfill N`): after the recent and wanted weeks, up to N weeks the app has only
  in the old format (`GET /api/cache/weeks` -> `old_only`, newest first), `--backfill-delay` (20 s) apart, 2 requests
  at a time; a week NOAA is too busy for is tried once more after 30 s, then left for the next run (backfill failures
  don't fail the run; recent-week failures do). No new week starts after `--max-minutes` (40). The server's index is
  the state, so it resumes by itself. Days are fetched once per run (the 10 recent weeks share 16 days: 16 downloads,
  not 70). A week is uploaded only if the Natural Earth land mask loaded. The workflow runs it twice a day with
  `--backfill 24` (`workflow_dispatch` takes `backfill` and `dates` inputs). Time: about 40 s a week (7 days ~10 to
  15 s from GitHub, encoding 3.6 s, the upload, 2 s + 20 s pauses), so 24 a run (~16 min) and ~48 a day: the ~320
  saved weeks on Render (Oct 2026) take about a week. Faster by hand: `gh workflow run seed-sst-cache.yml -f
  backfill=60`, or locally `CACHE_UPLOAD_TOKEN=... .venv/bin/python tools/sync_cache.py --count 0 --no-wanted
  --backfill 50`. Render never asks NOAA for any of this.
- **Tests**: `tools/test_sst_grid.py` (format round trip, codes, Auto range, sizes, old entries, the weekly cache and
  eviction order, the route never asking NOAA, the seeder's order, resume, 503s, rate limit and time cap against a
  mocked NOAA and app), `tools/test_sstengine.mjs` (the engine in the real page: readouts vs the Python decode, pixels
  vs `colorFor`, placement at zoom 11 across a sharp front, palettes, ranges, stepped, isotherms, breaks, "haze"
  ignored, crossfade, reduced motion, histogram, Fit to view, an old week, a failed download; the coast: no filled
  cell ever read, filled water drawn and filled land cleared, nearShore, the SST cleared on OSM land with no isotherm
  there, the rim at zoom 11, the panes' order, interpolation off at low zoom and bilinear at high zoom),
  `tools/perf_sstengine.mjs` (frame times above; `--only coast` for the coast part).

### Data Flow
```
User picks date → Load week → _load_week(): a saved copy (weekly file, else an old entry), or get_sst_multiday()
  (22 s budget, 3 days at a time newest first, OISST only if MUR sends nothing; 0.1 F over the coverage box)
  → sstgrid.entry_from_fetch(): orient → mask land (Natural Earth) → 0.1 F codes → GOSST1 (gzip -6) + Auto range
  → sst-store: meta, dates, bounds, Auto range, grid.url (~2 KB; no pictures)
  → memory (_raw_data_cache, 2 weeks): the bytes + float32 arrays for the measure panel
  → disk: sst/weeks/<end>_week.json.gz, written in a background thread (one file per week)

Browser (assets/sstengine.js, window.SSTEngine):
  sst-store → SSTEngine.setWeek() → GET /api/sst/week/<end>.bin (gzip, from memory or disk, never NOAA)
  → decode → per-day canvas through the color table → strips placed by Web Mercator on an L.Canvas (sst-pane)
  → "ready": the loading overlay goes; the day slider → setDay() (crossfade); Color strength → setOptions({opacity})
  → taps: SST.classify → click-pos → SST.selection() card from SSTEngine (no server trip); measure: render_selection

GFW Fishing Activity (separate data path):
  fetch_sst_data writes the served dates to the gfw-range store
  → toggle_layers builds the GFW layer (only while ticked) with ?dr=START,END
  → Leaflet requests /api/gfw/{z}/{x}/{y}.png?dr=START,END
  → Flask proxy reads dr from the request, calls GFW generate-png (once per range, cached)
  → Fetches styled tile with Bearer auth → returns PNG to browser
  → Tiles cached 24hr (Cache-Control: public, max-age=86400)
  → updateWhenZooming=False prevents proxy flood during zoom

Pre-cache (token-locked, rarely used: the seeder does this off-Render):
  /api/precache → _run_precache thread → for each date without a weekly file:
    get_sst_multiday() (MUR only, whole week) → sstgrid.entry_from_fetch() → put_week()
    → 120s hard timeout per date via _call_with_timeout
```

### Currents Page (`/currents`)
Animated tidal-current flow for eastern Long Island (Little Peconic → east of Block Island; south of Montauk → Watch Hill / Fishers), with a time-synced tide + current chart. Built to show why currents don't follow the tide table — e.g. at The Race slack comes ~2h40m *after* Montauk high/low water, at Plum Gut ~1h35m after.

Three views (sidebar "View" control; a "How it works" modal opens on a first visit):
- **Today** (default): typical currents for any day 2024–2030 from that day's real Montauk tide times and ranges — the **tide-stage atlas** evaluated client-side from Montauk high/lows bundled in the atlas meta (no live model, no runtime dependency except an optional NOAA fetch of the selected spot's own prediction for the chart/badge, with fallback). Opens paused on "now"; "Now" button returns there.
- **Tide cycle**: one typical Montauk cycle LW → HW → LW at Neap / Average / Spring strength.
- **Example weeks**: hourly model output incl. weather — supermoon, summer spring + neap, Hurricane Sandy (Oct 2012; replaced Blizzard Jonas: in fishing season, biggest modeled surge at Montauk, +3.1 ft).
- Until the atlas exists in the manifest (deploy before upload), the page opens on Example weeks with the other views disabled.

```
Atlas build (off-Render: build-currents.yml source=atlas, or locally)
  tools/build_tide_atlas.py
    hindcast May 1 – Nov 1 2016 (4,416 h), surface + depth-avg, streamed week by week
      (gridded int8 frames + NOAA JSON cached under build/atlas-work; reruns download nothing)
    phase phi: two segments from Montauk high/lows (HW→LW = 0→0.5, LW→HW = 0.5→1), 24 bins,
      bin centres (b+0.5)/24; range R(t): each half-cycle's |H−L| at its mid-time, linear
      between mid-times (no step at HW/LW), clamped to the season's range
    per bin: least squares of 3 "tent" basis fields at the 10/50/90th R percentiles
      (linear interpolation, continued past the ends) → 72 frames (basis·24 + bin), GOCUR1
    per-cell skill (share of variance explained) + residual RMS → haze + "Confidence here"
    NOAA: 30-day interval=30 curve per station fitted the same way → typ[3][24] + median
      lags; Montauk 6-min tide shape; high/lows 2024–2030 bundled; Neap/Average/Spring
      presets = 10/50/90th R percentiles of 2024–30 (not 2016: lunar-node peak)
    guards: fit coverage, The Race vs NOAA typical, 2026 slack check, Race-area skill,
      sizes; report: out-of-sample replay of example weeks, day/night aliasing check
    → atlas-2016_{surface,davg}.bin.gz (~0.9 MB each) + _meta.json.gz (~0.1 MB);
      manifest "atlas" entry (incl. presets, dates); uploaded only with --upload / publish

Week build (off-Render: local, or .github/workflows/build-currents.yml)
  tools/build_currents.py
    NECOFS FVCOM GOM3 (UMass Dartmouth) over OPeNDAP:
      hourly hindcast 1978→2016 for the curated weeks in data/currents_weeks.json,
      or the live GOM3 forecast (offline since ~Oct 2026; daily job exits 0 until it returns)
    → surface u,v (siglay 0) + depth-averaged ua,va for the region's mesh elements
    → element values averaged to nodes → barycentric onto a 221×126 grid (~400 m)
    → int8 (0.025 m/s per unit) → GOCUR1 binary (format in data/currents.py), gzip
    + NOAA CO-OPS predictions: Montauk tide 8510560 (6-min + H/L) and ~86 current
      stations (30-min curves + MAX_SLACK events) + model water level → <week>_meta.json.gz
    → POST /api/currents/upload (CACHE_UPLOAD_TOKEN); manifest.json uploaded LAST

Serve (Render; no request-time processing)
  GET /api/currents/manifest.json                     max-age 60
  GET /api/currents/<week>_<surface|davg>.bin.gz      Content-Encoding: gzip,
  GET /api/currents/<week>_meta.json.gz               max-age 1 day, ETag/304
  files in CURRENTS_DIR = $CURRENTS_DATA_DIR or $SST_CACHE_DIR/currents
  (/var/data/cache/currents on Render); names checked against FILE_RE

Client (assets/currents.js → window.Currents)
  L.Map.addInitHook grabs the dash-leaflet map whose container id is "currents-map"
  views are "timelines": S.t in [t0, t1) looping; weights(t) → frame weights
    (week: 2 hourly frames; date/cycle: 2 basis × 2 phase bins from tideAt()/tent());
    x mapping for the chart (wall time for date/week, seconds for cycle)
  once per animation frame the weighted frames are blended into S.cur (water cells
    only); the particle layer (pane z 450) samples it bilinearly; trails = destination-
    in fade + 'lighter' strokes, coloured by speed
  low-confidence haze (pane 455): canvas from skill + residual RMS → L.imageOverlay
  NOAA station dots (pane 470) coloured flood/ebb/slack (typical curve in date/cycle,
    live NOAA for the selected spot once fetched); click → select (+ set_props)
  Plotly chart drawn into #currents-chart (purged when the axis type changes):
    Montauk tide, station current (NOAA / typical solid, model dotted), slack + max
    markers, "now" line; Plotly hover OFF — one overlay-div time line with our own
    readout (time, tide, currents); mouse hover previews that moment on the map
    (playback holds, leaving returns); click/tap/drag sets the time + pauses
  badge: week = median lags this week; cycle = typical lags; date = that day's NOAA
    slack/max times; + "Confidence here" from the skill map
  setters only record state; one coalesced apply() loads what the view needs (a cold
    Today load fetches only manifest + atlas meta + one atlas field + one NOAA call)
  one requestAnimationFrame loop (~30 fps); nothing per frame touches Dash
```

Each week ≈ 2–2.5 MB per depth + ~70 KB meta (under Render's ~7 MB response limit). Validated against NOAA: model surface current at The Race / Plum Gut / Montauk correlates 0.94–0.99 with predictions and gets slack timing within ~10–35 min; peak speed in the narrowest gaps runs ~25–30% low (the ~1 km mesh smooths ~1.5 km-wide jets). The sidebar says so.

Atlas accuracy (full-season build, Oct 2026): share of the model's flow the typical cycle reproduces in weeks it wasn't built from — Race/Plum Gut/Fishers 87–96%, Gardiners/Peconics 78–89%, Block Island Sound 65–83%, ocean side S of Montauk 28–58% (hazed). Slack timing vs NOAA over all of 2026: The Race median 26 min, **biased late** (+26 min mean — the model's own timing at The Race; 90% within 46 min); Plum Gut median 13 min (90% within 33). The "How it works" modal (`layout/currentsview.py:_about_body`) quotes these — update it if the atlas is rebuilt.

#### Harbor-inlet estimates (Lake Montauk, Napeague, Accabonac, Three Mile, Northwest Creek, Sag Harbor Cove)
NECOFS's ~400 m grid has no water inside these harbors (Accabonac: 3 cells), so their inlet currents are computed from the tide, client-side, in every view:
```
Build (local; tools/build_inlets.py → data/inlets.json, committed — ships with the code)
  per harbor (INLETS): DEM tile, seed point inside, cut line land→land across the narrowest point
  harbor area by water level (NAVD88 −1.2…+0.8 m): NCEI DEM_all ImageServer (CUDEM 1/9″),
    flood-filled from the seed with the inlet cut off
  inlet: survey dimensions where they exist (Napeague: PEP 2012 — 160 m², 55 m wide, 670 m),
    else the DEM along the cut, floored by NOAA chart depths ("min_depth_m") where lidar misses
    the channel; channel length by hand (the narrow reach); marker = deepest point on the cut;
    flood/ebb = square across the cut, flood toward the seed (Napeague set by hand: it bends)
  bay tide outside: Montauk 8510560 high/lows + a NOAA station's median offsets and range ratio
    over a year (8511171 Threemile entrance, 8510502 Montauk Harbor entrance, 8511629 Sag
    Harbor), or interpolated between two stations by straight-line distance
  datum: Montauk MLLW/MSL vs NAVD88 (mdapi) + sea-level rise since the 1983–2001 epoch (0.12 m)
  report (typical timing vs Montauk → the "How it works" table), Lake Montauk check vs NOAA
    inside/entrance ("check"), selftest; harbors sorted east → west (the Spot list order)
Page (dcc.Store currents-inlets → Currents.setInlets)
  inletRun(): (L/g) dv/dt = Δη − r v|v|,  d(harbor)/dt = Ac v / A(harbor level);
    backward Euler (quadratic in v), dt 60 s, 24 h spin-up (cycle view: 3 cycles);
    tide from each view's tl.hilo() (bundled / week / synthetic cycle high-lows, cosine rule)
  inlet spots join S.stations (estimate: true); arrow marker in S.inletLayer (always shown);
  chart = view's tide traces + harbor tide (dashed) + inlet current; badge tagged "Rough estimate"
  "How it works" table (layout/currentsview.py:_inlet_table) from each inlet's report
```
Short, wide inlets (Lake Montauk, Accabonac, Northwest Creek, Sag Harbor Cove) don't choke: slack comes within minutes of high/low water just outside, which itself runs later westward (Sag Harbor +95/+75 min vs Montauk). Napeague and Three Mile Harbor have long, narrow channels that hold the harbor's tide back (slack 1–2 h after Montauk HW). To add a harbor: an `INLETS` entry, rerun the builder, check the report and the DEM-vs-chart throat line it logs, commit `data/inlets.json`.

## Critical Lessons Learned

### Incident 2026-10-16: every route stopped answering (runbook)
Full write-up: `docs/incident-2026-10-16.md`. About 10 minutes after SST sprint 1 went live, every route (static ones too, e.g. `/api/currents/manifest.json`) timed out for 11 minutes until a redeploy, with nothing in the log: no traceback, no WORKER TIMEOUT.
- **What happened**: all routes share one gunicorn worker with 16 request threads, and requests that wait on an outside server hold them. NOAA was unreachable from Render (each try waited out the connect timeout, then errno 101), so each uncached week held a thread for the whole 22 s. Then the fishing-activity layer was turned on and GFW tiles kept coming: the tile proxy called GFW's generate-png under one process-wide lock and remembered no failure, so the tiles queued behind it one 15-30 s attempt at a time. When GFW is slow rather than down, requests' `timeout=15` (a per-read timeout) never fires, so the queue never drained and nothing was logged. The gthread main loop kept heartbeating, so gunicorn saw nothing wrong. Reproduced locally (gunicorn as production, `tools/netsim`); the stacks showed 15 threads at `with _gfw_style_lock:` and one in `ssl.read` under `_get_gfw_style`. NOAA dripping hangs the same way (`erddap.http_get` iter_content).
- **Rules since**: no lock is held across a network call; every outside call goes through `data/outbound.py` (a whole-call deadline that holds even against a drip, its own threads, a cap on calls in flight and on callers waiting, a breaker that opens on connect failures); failures are remembered briefly (a GFW range for 60 s, a week for 60 s, the newest-day lookup for 5 min) and logged at most once a minute; at most `SST_NOAA_READERS` request threads wait on NOAA; every wait has a timeout (`_call_with_timeout`, never `with ThreadPoolExecutor(...)` around a timed `result()`: leaving the block waits for the work).
- **When the site hangs again, before restarting**: in the Render shell, `ps aux | grep gunicorn` and `kill -USR1 <worker pid>` (or the master's pid: gunicorn forwards USR1 to its workers). Every thread's stack goes to the log (faulthandler, `Thread 0x... (most recent call first)`), and the server keeps running. While a thread is still free: `curl -H "X-Upload-Token: $CACHE_UPLOAD_TOKEN" https://offshore-sst-map.onrender.com/api/debug/threads` lists the requests running and their ages, each upstream's calls in flight and breaker state, NOAA reader slots, week locks, recent failures and every thread's stack (403 if the token isn't set, 401 if wrong).
- **What the log shows by itself now**: "Slow request: GET /... running for 61s; its stack: ..." for any request over `SLOW_REQUEST_S` (60 s; the watchdog checks every 10 s); "All 16 request threads busy for over 60s; every thread's stack follows" plus a full faulthandler dump (at most every 10 minutes); "NOAA ERDDAP (coastwatch.pfeg.noaa.gov) is failing (...): not asking it for 60s" / "... answers again"; "Global Fishing Watch is failing ..."; "GFW generate-png failed: ..." and "GFW tile ... not fetched: ..." (once a minute per kind).
- **gunicorn >= 24's gthread worker** hands each accepted connection straight to a pool thread, which waits for the request on it (24 and 25 with no timeout; 26 for 5 s, then it goes back to the poller). 23.0.0 waits in its poller until the socket is readable. So 16 connections that connect and send nothing freeze every route on 24 and 25, silently, and stall it about 5 s on 26 (23.0.0 answers in 0.01 s). **Pinned to `gunicorn==23.0.0`** since the relaunch (it used to be `>=21.2.0`, so production ran whatever pip resolved: 26.2.0 in Oct 2026). `tools/load_sst_outage.py` checks it (16 idle connections, then a request within 2 s): 23.0.0 passes every scenario; check "Starting gunicorn 23.0.0" at boot.

### NOAA Blocks Render's Datacenter IP — Data Must Be Fetched Off-Render
*(Lifted as of 2026-10-10 — see Architecture → SST Data Sourcing. Kept for the diagnosis technique and in case it returns.)*
- **The symptom**: recent dates on the live site show a red "SST fetch timed out after 90s" (or "No compatible SST dataset found") box, while localhost works perfectly. **The cause is not in the code** — NOAA's firewall blocks Render's datacenter IP at the network layer. Confirmed in the live Render logs: `ConnectionError: Network is unreachable` (coastwatch.pfeg), `ConnectTimeout` / `Connection reset by peer` (upwell), `ReadTimeout` (coastwatch.noaa.gov tarpit). It worked from Render months ago; NOAA tightened anti-cloud filtering since.
- **`erddap_search` swallowed exceptions silently**, so the failures looked like a generic 90s timeout with zero log breadcrumbs. It now logs the exception type per server — that's how the block was confirmed (`ConnectTimeout`=firewall drop, `ReadTimeout`=tarpit, `403`=WAF/User-Agent). (Since Oct 2026 there is no search step; every failed request is logged with its kind: busy, timeout, network, blocked, dead, missing.)
- **A User-Agent header is necessary but not sufficient**: NOAA's WAF 403s the default `python-requests` UA, so `data/erddap._HEADERS` sends a real one. But that only addresses the 403 variant — the network-level IP block is the real problem, and **no fetch-code change can fix it**.
- **The fix is architectural**: fetch where ERDDAP is reachable (localhost / GitHub runners — both verified not blocked) and push cache files to Render via `POST /api/cache/upload`. See *Architecture → SST Data Sourcing*. The public AWS MUR Zarr mirror (`s3://mur-sst`) was evaluated and rejected — its time axis is frozen at ~Jan 2020.
- **If the live map breaks for recent dates**: check the seed workflow first (`gh run list --workflow=seed-sst-cache.yml`), not Render's ERDDAP path. Re-seed manually by running `tools/sync_cache.py` from a non-blocked IP with `CACHE_UPLOAD_TOKEN` set.

### GitHub Actions Schedules Die After 60 Idle Days
- In a public repo, scheduled workflows are **silently disabled** after 60 days without repository activity. That stopped "Seed SST cache" on 2026-08-30 (last commit was July 1) and nothing alerted — the SST map only kept working because NOAA had lifted its block. Check with `gh workflow list --all` (state `disabled_inactivity`); re-enable with `gh workflow enable "<name>"`.
- **`.github/workflows/keepalive.yml`** runs weekly and pushes a heartbeat commit (`.github/keepalive.txt`) only when `main` has been idle 45+ days. A real commit is the documented activity signal; whether an API re-enable resets the timer is undocumented, so we don't rely on it. Render auto-deploys `main`, so a heartbeat commit also redeploys the app (a harmless restart: the disk cache survives).

### NECOFS / FVCOM Gotchas (currents pipeline)
- **The live GOM3 forecast is listed but missing**: THREDDS `forecasts.xml` advertises `FVCOM/NECOFS/Forecasts/NECOFS_GOM3_FORECAST.nc`, but the file 404s (Oct 2026). The `NECOFS_FVCOM_OCEAN_GLOBAL_FORECAST.nc` that *is* live is **daily-mean** — tides average out, useless for currents. The hourly 30-year hindcast (`fvcom/hindcasts/30yr_gom3`, 1978-01-01 → 2017-01-01) works.
- **Nothing on UMassD's THREDDS is newer than 2016**: `catalog/archives.xml` holds only 2010–2014 forecast archives (GOM3v11/v12/v13, MassBay, waves). So storms like Henri (Aug 2021, Westerly landfall) can't be example weeks; in-season storms in the hindcast, by modeled surge at Montauk: Sandy Oct 2012 +3.1 ft, Bob Aug 1991 +2.2, Hermine Sep 2016 +2.0, Irene Aug 2011 +1.8.
- **2016 sits near a lunar-node peak**: M2 is ~7% stronger than in 2026, so tide-range presets taken from 2016 overstate today's tides. The atlas takes Neap/Average/Spring from the 2024–30 range distribution; Today mode is immune because it blends by the day's actual range in feet.
- **The model's slack at The Race runs ~25 min late vs NOAA** (all of 2026: mean +26 min, 90% within 46) while Plum Gut is close (median 13 min). It's the model, not the atlas method — the hourly weeks show the same 16–36 min. Don't promise "slack within 20 min" at The Race; the chart/badge show NOAA's own times.
- **NOAA *subordinate* current stations have no curve** — only slack and max-current events, whatever `interval` you ask for (72 of the region's 86, all the `ACT*` ones; e.g. Montauk Point = The Race with per-phase time shifts of −74 to −124 min and ×0.7 flood / ×0.5 ebb, from mdapi `?expand=currentpredictionoffsets`). Treated as a curve, the chart drew a zigzag (7 points a day) and the atlas fit left most phase bins empty → 0 kn → those dots read "slack" most of the time. Detect "events only" (median spacing > 45 min) and rebuild with NOAA's own rule — quarter sine slack ↔ max, half cosine between maxima (`densify` in `tools/build_tide_atlas.py` and `assets/currents.js`). Zero-crossing code must count exact zeros (NOAA's slack points are 0.0).
- **NOAA current predictions are capped at 31 days per request** (`interval=30`), but `MAX_SLACK` events and Montauk high/lows come back for a whole year in one call, and 6-min tide heights for 6 months. The atlas builder fits each station from one 30-day curve (Aug 2016 covers two spring/neap cycles).
- **Don't read `Itime`/`Itime2` on the hindcast**: it's an aggregation of ~470 monthly files, and those variables make THREDDS open every one (hung 10+ min). The aggregated `time` coordinate is cached and fast; it's float32 MJD (~6-min resolution at modern dates), so round to the hour.
- **Month boundaries repeat an hour** in the aggregation (467 duplicate steps). A week crossing one has 170 raw steps for 169 hours; `window_steps()` keeps the first copy. Without it every later frame is shifted an hour — fatal for slack timing.
- **Velocities are element-centred** (`lonc/latc`; `nv` is 1-based); `siglay` index 0 is the surface; `ua/va` are depth-averaged. Average elements → nodes, then barycentric interpolation inside mesh triangles; grid points outside the mesh are land.
- **Model water level (`zeta`) isn't on the gauge's datum** — a MSL→MLLW shift left it 0.7–1.2 ft low every week. Align by the week's median difference so only weather (surge) separates it from NOAA's prediction.
- **~1 MB/s from smast.umassd.edu**; the region's elements span 47% of the index range, so a week (4 variables × 169 h) is ~115 MB, ~2–3 min.
- **NOAA "no predictions" errors are deterministic** — don't retry them (`NoRetry`); retrying cost ~18 s per station. `LIS1001` The Race and `LIS1012` Plum Gut are harmonic (pass `bin=<currbin>`); most `ACT*` stations are subordinate. 86 current-prediction stations fall in the region.
- **NOAA CO-OPS rate-limits per IP (~160 calls, then `403 Forbidden`)**: the first GitHub Actions build fetched a week's ~175 prediction calls with 4 threads (~21 req/s) and the runner was 403'd on the next week; a sequential 2 req/s test from home internet also got one 403, at call #162. Calls are now sequential, `NOAA_MIN_INTERVAL` = 1 s apart (~3 min/week), the spacing doubles (max 4 s) after each 403/429, and throttled calls back off 60/120/240 s (`Throttled`). Only "no data" responses skip a station — a network error or throttle fails the week, so a throttled run can't publish a week with stations silently missing. A failed week is skipped (its old version stays live), the rest still publish, and the run exits 1.
- **NOAA can return an empty list for a station it covers**: in the first production build ACT2776 (Mulford Point) came back with zero rows in one week, beside a 504 for another station, and was dropped without a log line. `station_cp()` retries an empty answer once, and every dropped station is now logged. The page tolerates a station missing from one week (selection is ignored; switching weeks falls back to The Race), but the dropdown label won't match, so rebuild that week.

### Harbor Inlets (estimates)
- **Lidar DEMs miss inlet channels.** NCEI's 2015 CUDEM (topobathy lidar) shows Napeague's west inlet as a 21 m², 0.4 m-deep gap; the 2012 bathymetric survey measured 160 m² (8–10 ft deep, 180 ft wide). Fast, turbid inlet water defeats lidar and the gap gets interpolated from the shoulders. With the DEM throat the model "chokes" the harbor to a tide of a few inches — a red flag that sent us looking for the survey. Use surveys or charts for the throat; the DEM only for the harbor's area. (Chart soundings agree with the DEM within ~0.35 m elsewhere, but none sit in the throat.)
- **Napeague has one inlet now.** The east inlet by Goff Point closed around 2007 (Peconic Estuary Program report), so all exchange goes through the west inlet at Lazy Point, which widened from 64 ft (1970) to 180 ft (2010); the county dredged it in Oct 2014 and homeowners report more widening since. A bigger inlet means less lag (≈30–40 min after Montauk instead of ≈70) — the first thing to recalibrate from on-the-water observations.
- **NOAA "Goff Point, 0.4 mile NW of" (ACT2471) is not the harbor inlet**: it sits in the bay at the head of the 10–12 m channel west of Hicks Island and floods toward 225° (along that channel). Its slack (~1h15–1h40 after Montauk HW) is the bay's.
- **The tide arrives later westward through Gardiners Bay** (NOAA vs Montauk Fort Pond Bay): Threemile Harbor entrance HW +65 / LW +39 min, Sag Harbor +93 / +74, Little Gull +39 / −2. NECOFS agrees in direction but runs ~20–35 min later than NOAA west of Napeague, and its Napeague Bay amplitude looks wrong (coarse mesh) — so the bay tide outside each inlet is interpolated from NOAA stations, not taken from the model.
- **Momentum matters for slack**: a friction-only (Keulegan) model puts slack at the moment bay and harbor levels cross; with the 670 m channel's inertia the water keeps running and slack comes ~13 min later. The slack window (< 0.5 kn) is ~30 min either way. Bigger tides choke more (friction ∝ v²): ~1h30 lag on supermoon tides vs ~1h10 typical.
- **Lake Montauk is the check case** (NOAA predicts inside 8510448 and at the entrance 8510502): NOAA ±5 min, the method 0 / +2 min with the DEM's channel (deep and dredged, so lidar sees it). It shows the method doesn't invent lag; it can't validate Napeague's lag — only on-the-water slack times can.
- **NOAA ENC "Dredged_Area" polygons give each maintained channel's depth and width**: `encdirect.noaa.gov/.../enc_harbour/MapServer/228` (DRVAL1 = m below MLLW; intersect the polygon with the cut for the width; soundings are layer 76). Lake Montauk Reach A 4.9–5.0 m × ~44 m (USACE survey May 2026), Three Mile 1.8 m × ~31 m (1996), Northwest Creek 1.8 m × ~45 m (1995), Accabonac 2.4 m (1996; on the approach, not in the gap). Lidar saw the deep dredged channels (Lake Montauk, Three Mile) but missed the shallower ones (Napeague, Northwest Creek ~0.5 m vs 2.4 m soundings, Sag Harbor bridge ~1 m vs 1.8–2.7 m).
- **Three Mile Harbor's lag is the most sensitive**: a 4.2 km² harbor behind a ~450 m jetty reach of ~163 m². Across plausible channel sizes and lengths, slack runs ~1h10–2h20 after Montauk HW (163 m² × 450 m → 1h55). An on-the-water slack time at the jetties would pin it down.
- **The U.S. Coast Pilot 2 (ch. 7) gives the only published inlet speeds**: Lake Montauk entrance 1.2 kn flood / ~0.5 kn ebb, Three Mile Harbor ~3 kn. They run 30–40% above the model's cross-inlet averages (typical per-tide peak, `typical_flood_kn` in the report), as expected mid-channel. The model can't reproduce Lake Montauk's weak ebb (flood/ebb asymmetry). Town / county figures for harbor areas (East Hampton LWRP, Town GIS 2022) match the DEM hypsometry within a few percent. Dredging history: Accabonac (county, 8 ft MLW, 2013/2020/2023), Northwest Creek (county, Nov 2023), Lake Montauk deepened to 17 ft MLLW (USACE, done July 2026).
- **NOAA has no tide station inside any of these harbors**; "Threemile Harbor entrance" (8511171, with historic data and harmonics) sits ~200 m out in the bay, so it is the outside tide.
- **NOAA's sea-level trend API answers in `trendUnits: "inches/decade"`** (Montauk 1.42 → 3.6 mm/yr). NOAA tide predictions exclude the ~0.12 m rise since the 1983–2001 epoch; it matters when tide heights meet a NAVD88 DEM.
- **Keep `inletRun()` in `assets/currents.js` in lockstep with `tools/build_inlets.py`**: `window.Currents._inletSelftest()` should report `maxErr` ≈ 5e-5 (the stored values' rounding). The builder computes its selftest from the *live* atlas (3-decimal heights); an older local atlas copy (2 decimals) drifts ~0.006 kn.

### Tide Height ≠ Tidal Current (the point of /currents)
- NOAA publishes current predictions separately from tide predictions, and in the Race / Plum Gut / Montauk system slack and max flow are phase-shifted from local high/low water. Supermoon week 2015: The Race slack ≈ 2h40m after Montauk HW/LW, max flood ≈ 15 min–1 h *before* HW; Plum Gut slack ≈ 1h40m after. So "fish the slack at high tide" by a Montauk tide table is off by hours, and two passages a few miles apart turn about an hour apart.
- Wind and surge push real flow off the tide-only predictions: during Blizzard Jonas (Jan 2016) the model's Montauk current peaked 3.2 kn vs NOAA's 2.7 with water ~2.3 ft above its usual offset; during Hurricane Sandy (now the storm example week) the model puts Montauk +3.1 ft above the predicted tide on the evening of Oct 29, 2012.
- **The currents are locked to the tide cycle in the passes, so a typical cycle works there**: 2026 NOAA predictions put The Race's slack 2h38 after Montauk HW (80% within about ±20 min) and its strength varies ~±20% with the range; that's why the default view is a tide-stage atlas, not a forecast. It fails on the ocean side south of Montauk (wind and shelf currents dominate) — hazed on the map.

A "Click to set this time" hint appears only while previewing a time other than the set one. Legend names say what each line is ("Montauk tide, ft (NOAA)", "<spot> current, kn (NOAA)", "<spot> current, model") and list the slack / strongest-flood markers when the chart is ≥ 1000 px wide.

- **Dash 4 dropdown menus render inline**, inside the dark sidebar, so they inherit its light text (white on white). `#sidebar-col .dash-dropdown-content` needs the navy override too, not just `.dash-dropdown-value`.
- **The date input has a fixed width** and overflowed its flex slot in the narrow sidebar, covering the "Now" button (clicks hit the calendar). The date row wraps and the input is `width: 100%`.
- **Leaflet 1.9 tiles use `mix-blend-mode: plus-lighter`** (its fix for seams in opaque basemaps). On a semi-transparent overlay tile layer (the Esri place-name pane) it brightens every tile edge into faint lines across the map — on iPad and in Chromium, even at whole zoom levels. Give overlay tile layers `mix-blend-mode: normal`. Don't "fix" seams by overlapping tiles 1 px: with plus-lighter the overlap itself draws bright lines.

### Dash 4.0 Gotchas
- **Never use clientside callbacks that manipulate DOM for elements also controlled by server callbacks.** Dash's virtual DOM reconciliation won't see the DOM change, so server callback updates get silently skipped, leaving the UI stuck. We burned multiple iterations on this with the Fetch button getting permanently disabled.
- **`allow_duplicate=True` requires `prevent_initial_call=True`** (or `"initial_duplicate"`). Dash 4 enforces this strictly.
- **`dbc.Spinner` v2 uses `spinner_class_name`**, not `className`. The constructor will error.
- **Callback timeouts are browser-side**, not server-side. If a synchronous Dash callback takes >30s, the browser gives up with "server did not respond" and the callback system can get stuck. Once stuck, subsequent clicks don't fire. Solution: keep callbacks under 30s or use time budgets.
- **Changing callback inputs/outputs changes the callback hash.** Browser-cached JS from a previous session will 500 with "Callback function not found." Users must hard-refresh after callback signature changes.
- **Avoid unicode icons in button labels.** Characters like ⏸ (U+23F8) and ❚❚ (U+275A) render inconsistently across browsers/OS. Use plain text labels ("Play"/"Pause") instead.
- **Server must be restarted for code changes to take effect.** Committing and pushing is not enough — the running Dash dev server serves from memory. Preview server must be stopped and restarted.
- **Dash 4 CSS class names differ from older versions.** Date picker uses `.dash-datepicker-input` (not `.DateInput_input`). Dropdown uses `.dash-dropdown-value`, `.dash-options-list-option-text` (not `.Select-value-label`). Calendar uses `.dash-datepicker-calendar`. Always inspect the actual DOM to find the right selectors — don't guess from docs for older versions.
- **Dark sidebar + white inputs require aggressive CSS overrides.** Dash components inherit text color from their parent. When the sidebar has light text, every input/dropdown/calendar inside it also gets light text. Must use `!important` on the specific Dash 4 class names for each component.
- **Dash 4.0 finishes its setup on the first request, and that races** (found Oct 16, 2026): `Dash._setup_server` (a `before_request` hook) walks `assets/` and builds the script and stylesheet lists, but sets its "done" flag *before* doing so, with no lock. After a boot the first page loads arrive together (gunicorn's listening socket queues them while the worker imports app.py), and the threads that skipped the half-done setup sent pages with **no `/assets` at all**: no sst.js (`window.SST` missing: map taps and the GFW retry dead), no labs.js, currents.js or gotone.css. 8 of 32 cold-boot /sst loads, 4 at once. Fix: `app._finish_dash_setup()` runs `_setup_server()` once at import, after every callback is registered. Check with `node tools/boot_sst_pages.mjs`. If a Dash upgrade drops `_setup_server`, the app logs a warning at boot.
- **Initial overlay must be set by a server callback, not clientside.** Clientside callbacks that depend on `dcc.Store` data from background or long-running callbacks can fire before the store data is fully propagated. Use `render_static_layers` (server callback) to set the initial overlay, and clientside callbacks only for frame changes.

### Background Callbacks (`background=True`) — Do NOT Use on Render
- **Dash background callbacks use DiskcacheManager** to poll for results. The full callback return value is serialized and delivered via a polling HTTP response.
- **Render's proxy returns 502** when the polling response exceeds ~7-10 MB. Our original payload (~26 MB with raw arrays) caused consistent 502s.
- **Even with reduced payload**, background callbacks add complexity (diskcache dependency, forked processes) for marginal benefit on a single-worker setup.
- **Solution**: Use synchronous callbacks. Keep the payload under ~7 MB by splitting raw arrays to server-side memory. The disk cache ensures most fetches return in <2 seconds.

### Payload Size Management
- **dcc.Store payload must stay under ~7 MB** for reliable delivery on Render.
- **Raw float arrays are the biggest culprit**: 7 days × ~93K floats × ~8 bytes/float = ~5 MB as numpy. These MUST be kept server-side.
- **Store payload contents** (since sprint 2): meta, dates, bounds, the Auto range and the week's URL, ~2 KB; the week's grid (~0.6 MB gzip) comes from `/api/sst/week/<end>.bin`. Before: 7 base64 PNG frames.
- **Server-side `_raw_data_cache`**: In-memory dict keyed by `"{end_date}_week"` (was `"{end_date}_{mode}"`). Stores the week's bytes, its store payload and float32 arrays for the measure panel. **Limited to 2 entries** (~25 MB each) via `_put_raw_cache()` to stay within Render's 512 MB. Oldest entry evicted when limit exceeded. **Populated BEFORE disk write** so clicks work even if disk write fails. Falls back to disk cache on miss (handles restarts).
- **Disk cache** (`data/cache.py`): Stores the FULL payload with raw arrays as **base64-encoded numpy `.npy`** format (v2) instead of JSON lists (v1). Written in a **background thread** to avoid blocking the callback response. Backward-compatible: reads both v1 and v2 formats.

### Memory Management on Render (512 MB)
- **Never use `.tolist()` for disk cache serialization.** Converting numpy float64 arrays to Python lists triples memory usage (8 bytes/float → ~28 bytes as Python object). On Render's 512 MB, this can OOM the worker.
- **Use `_serialize_array()` / `_deserialize_array()`** — base64-encoded numpy `.npy` format. Only 1.3x memory overhead vs 3x+ for `.tolist()`.
- **Always populate `_raw_data_cache` before disk write.** If the disk write OOMs or crashes the worker, the memory cache is already set and clicks work. The callback response is also faster since the disk write happens asynchronously.
- **Disk write in background thread** — `threading.Thread(target=_write_disk_cache, daemon=True)`. Non-blocking, so the fetch callback returns immediately to the browser.
- **Pre-cache uses raw-only mode** (`_precache_single_date`): Processes one day at a time, serializes immediately, frees the numpy array before moving to the next. Running percentiles instead of `np.concatenate` avoids the 16 MB temporary allocation. Skips PNG rendering entirely. Peak memory ~30-35 MB per iteration vs 65-70 MB with `_build_payload`.
- **Per-date timeout**: 120s hard limit via `ThreadPoolExecutor` prevents ERDDAP hangs from blocking the worker. Timed-out dates are skipped and logged as errors. The fetch inside it is MUR only and whole weeks only (`require_full`), with a 100 s budget, 2 days at a time.

### Global Fishing Watch Integration
- **GFW 4Wings API**: Two-step process — POST to `generate-png` to get a styled tile URL template with color ramp, then GET individual tiles at `{z}/{x}/{y}` using that template.
- **Server-side tile proxy** (`/api/gfw/<z>/<x>/<y>.png`): Flask route proxies GFW tile requests with Bearer auth so the `GFW_API_TOKEN` stays server-side (Leaflet can't add custom auth headers to tile requests).
- **SSL domain fix**: GFW's `generate-png` returns URLs pointing to `gateway.api.prod.globalfishingwatch.org` which causes `SSLEOFError` in Python. Must replace with `gateway.api.globalfishingwatch.org`.
- **Date range per request** (Oct 2026): GFW tiles use the days on the map. `fetch_sst_data` writes them to the `gfw-range` store, `toggle_layers` puts them in the tile URL (`?dr=START,END`), and the proxy reads and validates that `dr` (start <= end, at most 31 days, 2012 to today; bad = 400, missing = the newest week). There is no process-wide range any more: it used to be a module global set by whoever fetched last, so a second visitor on another week changed your tiles and the browser cached the wrong ones for 24 h.
- **Style cache**: `_gfw_style_cache` maps each date range to its URL template (32 ranges, oldest dropped). `generate-png` is called once per range (`_gfw_style`): the first tile makes the call (6 s at most, `GFW_STYLE_S`), up to 4 others wait for it up to 4 s (`GFW_STYLE_WAITERS`, `GFW_STYLE_WAIT_S`; the rest get 503 "busy"), and a failed range isn't asked again for 60 s (`_gfw_style_failed`). `_gfw_style_lock` only guards those dicts: it used to be held during the call, which is how the Oct 16 outage happened (Incident 2026-10-16).
- **Bounded calls**: generate-png and tiles go through the GFW upstream in `data/outbound.py`: at most `GFW_MAX_CALLS` (6) calls at once, 4 more tiles wait up to 3 s for a free one, and the rest are answered at once with **503 "busy"** (`Retry-After: 1`, no-store, no image in the body), as is a tile whose range's generate-png is still running after its 4 s wait. `assets/sst.js` (`gfwRetry`, an `L.TileLayer` init hook on `/api/gfw/` layers) asks for a 503 tile again after 0.5-1.2 s, then longer, up to 4 times. The body must not be an image: browsers show an image sent with an error status, and then Leaflet sees no error to retry. Checked in Chrome: 4 pages at zoom 9 (80 tiles at once) against a GFW taking 1 s a tile all showed every tile within 8 s. A tile fetch takes 6 s at most (`GFW_TILE_S`). Three connect failures or timeouts in a row open the breaker for 60 s: the layer is then empty, at once, instead of holding threads.
- **Loaded only when on**: the layer exists only while "Fishing activity" is ticked (same for the chart and bathymetry), so nothing is requested otherwise. `layout/mapview.GFW_NOTE` is a one-line explanation for the legend / How it works (AIS-based apparent fishing effort, mostly larger commercial boats; GFW's lag for the newest days is unchecked).
- **Graceful degradation**: If `GFW_API_TOKEN` env var is not set, proxy returns 204 (no content) and tiles are transparent. The checkbox still appears but does nothing. Empty tiles (GFW 404/204) come back as a 1x1 transparent PNG with 200, so browsers log no errors. When GFW fails (style or tile: down, busy, timeout, HTTP error) the tile is the same transparent PNG with `Cache-Control: no-store`, so the browser doesn't keep a blank tile for a day, and the failure is logged once a minute.
- **Layer z-index**: 420 (above SST at 410, below POI markers at 450) so fishing dots render on top of temperature colors.
- **Token**: JWT with 10-year expiry. Set as `GFW_API_TOKEN` env var on Render and locally.
- **AOI bounds clipping**: `bounds=[[38.80, -74.96], [43.80, -68.80]]` on the TileLayer prevents tiles from loading outside the SST coverage area. Reduces proxy requests and eliminates visual clutter.
- **Zoom-aware tile loading**: `updateWhenZooming=False` + `updateWhenIdle=True` prevents GFW tile requests from flooding the single worker during zoom animations. `keepBuffer=4` retains more off-screen tiles to reduce re-fetches on pan-back.
- **Server-side tile cache** (`_gfw_tile_cache`): In-memory dict caches both 200 and empty responses keyed by `(z, x, y, date_range)`. ~Half of tile requests are empty ocean, each saving a ~1s round-trip. Max 300 entries, oldest dropped first. Memory: ~5-10 KB per tile × 300 = ~3-6 MB max.
- **Browser cache**: `Cache-Control: max-age=86400` (24 hours). Historical GFW data is static, so aggressive caching is safe. Tiles for different date ranges use different proxy URLs (via `?dr=` param).

### Pre-Cache System
- **Endpoint**: `GET /api/precache` triggers background fetching of historical SST data for tuna season dates (Jun–Nov, weekly intervals, 2020–2025).
- **Status**: `GET /api/precache/status` returns JSON with `running`, `done`, `total`, `errors`, `cache_dir`, `cached_files`.
- **Raw-only mode**: Pre-cache uses `_precache_single_date()` which skips PNG rendering entirely. Processes each day individually (serialize → free → next), uses running percentiles instead of `np.concatenate`. Peak memory ~30-35 MB per iteration (down from 65-70 MB with `_build_payload`).
- **On-the-fly PNG rendering** (before sprint 2; old entries are now converted to the weekly grid instead, see SST data, cache and engine): When a user loads a raw-only cache entry (`frames: None`), or one whose frames aren't the current `frame_format` (saved before Oct 16, 2026; see ImageOverlay Is Stretched in Web Mercator), `_build_payload_from_disk_cache()` renders PNGs on-the-fly (~0.4 s on this Mac). A background thread then upgrades the cache entry with PNGs so subsequent loads are instant.
- **Per-date timeout**: 120s hard timeout via `_call_with_timeout` (a ThreadPoolExecutor shut down with `wait=False`). If ERDDAP hangs, the date is skipped and logged as an error instead of blocking the worker indefinitely. Before Oct 16, 2026 it was `with ThreadPoolExecutor(...)`, whose exit waits for the fetch, so the timeout never applied.
- **Query params**: `start_year`, `end_year`, `months` (comma-sep), `interval` (days between dates, default 7), `delay` (seconds between fetches, default 45).
- **Skips already-cached dates**: Checks disk cache before fetching. Safe to re-run after interruptions or worker restarts.
- **Cache persistence**: Render Persistent Disk ($0.25/GB/month) at `/var/data/cache`. Set via `SST_CACHE_DIR` env var. Cache survives worker restarts and deploys. Without persistent disk, Render's ephemeral filesystem wipes cache on every container restart.
- **MAX_ENTRIES**: 4000 in `data/cache.py`, a backstop only since sprint 2: eviction follows a disk budget, least recently viewed first (see SST data, cache and engine, Retention).
- **Timing**: ~1 date per 90 seconds (45s fetch + 45s delay on Render). Full 180 dates takes ~4-5 hours.
- **Idempotent**: Safe to call `/api/precache` multiple times. Already-cached dates are skipped. If the worker restarts mid-run, just hit the endpoint again to resume.
- **`raw_only` parameter on `_build_payload_from_disk_cache()`**: When `True`, skips PNG rendering entirely (returns `frames=[]`). Used by `_get_raw_data()` for click-lookup paths and pre-warm thread, where only raw arrays are needed.

### Render Deployment
- **Must use 1 gunicorn worker.** The `_raw_data_cache` is per-process. With multiple workers, a click request may be served by a worker that doesn't have the data. The disk cache fallback mitigates this, but 1 worker is the intended config.
- **16 threads per worker** (`--threads 16`): GFW tile proxy and click callbacks are I/O-bound. With threads, `requests.get()` releases the GIL during network I/O, so tile fetches and click lookups run concurrently. After zoom, ~48 GFW tile requests flood the proxy — with 16 threads, most run concurrently (3 rounds vs 12 with 4 threads), leaving threads free for click callbacks. Python's GIL keeps dict operations on shared state (`_raw_data_cache`, `_gfw_style_cache`, `_gfw_tile_cache`) atomic. Memory overhead is minimal (~50-100KB RSS per thread for I/O-bound work).
- **Start command must be set in Render Settings** (not blank — Render requires a value). Use: `gunicorn app:server --bind 0.0.0.0:$PORT --workers 1 --threads 16 --timeout 180`
- **Auto-deploy is ON**: pushes to `main` went live within ~2.5 min in Oct 2026 with no Manual Deploy (it used to be off). Treat every push to `main` as a production deploy — test locally first — and check the live asset afterwards (e.g. grep the served `/assets/currents.js`). `[skip render]` or `[render skip]` in a commit message skips that commit's deploy (docs-only changes); Manual Deploy in the dashboard still works.
- **Pre-warm thread** runs 15s after startup. Only loads from disk cache (no ERDDAP, uses `raw_only=True` to skip PNG rendering). Heavy ERDDAP fetches during startup starve the gunicorn worker and cause Render's health check to fail, hanging the deploy indefinitely.
- **Persistent Disk**: 1 GB disk mounted at `/var/data/cache`. Set `SST_CACHE_DIR=/var/data/cache` in Render Environment. Cache survives worker restarts and deploys. Without this, Render's ephemeral filesystem wipes cache on every container restart — the pre-cache system is useless without persistent storage.
- **`GFW_API_TOKEN` env var** must be set in Render Environment for fishing activity layer. Without it, the layer degrades gracefully (transparent tiles).
- **Health check failures**: Caused by ERDDAP stalls blocking the single worker. The pre-cache 120s timeout and GFW tile `updateWhenZooming=False` mitigate this. If the worker restarts, persistent disk preserves cache files.
- **Thread budget** (since the Oct 16 outage): at most 4 request threads wait on NOAA (`SST_NOAA_READERS`), at most 6 + 4 on GFW calls, each for a bounded time (NOAA one 22 s budget, GFW 3 s + 6 s), so a NOAA or GFW outage can't hold all 16 for long. Plus at most 4 tiles waiting up to 4 s for their range's generate-png (`GFW_STYLE_WAITERS`; the others get 503 "busy" and the page retries). Any request over 60 s is logged with its stack; `kill -USR1 <pid>` and `/api/debug/threads` show every thread (see Incident 2026-10-16).
- **gunicorn version: pinned to 23.0.0** (`requirements.txt`, since the Oct 16, 2026 relaunch; was `>=21.2.0`, which resolved to 26.2.0). From 24.0 the gthread worker waits for each new connection's request on a pool thread (24 and 25 with no timeout, 26 for 5 s), so 16 connections that send nothing hold every request thread; 23.0.0 waits in its poller (see Incident 2026-10-16). Everything passes on 23.0.0 with Python 3.12: the tests, `tools/load_sst_outage.py` (3 scenarios, now with an idle-connection check that 25.1.0 and 26.2.0 fail) and the smoke test. 23.0.0 has the gthread worker with `--threads` and the same flags as the start command; it has no `--control-socket` (25+ only). Check "Starting gunicorn 23.0.0" in the boot log after the deploy. Run the load test before moving off it.

### ERDDAP Behavior
- **MUR data latency**: about 1 day (on Oct 16, 2026 `time[last]` was 2026-10-15T09:00Z). Don't guess it: read `time[last]` (`latest_mur_date()`). The days under ~4 days old are preliminary and revised daily for 7 days.
- **A stop time past the axis maximum is an error** (404 "Stop is greater than the axis maximum"), even inside the last day. Request the dataset's stamp (MUR 09:00Z, OISST 12:00Z), never `T23:59:59Z`.
- **Overload**: coastwatch.pfeg answers 503 "Service Unavailable: There was a (temporary?) problem. Wait a minute, then try again" in bursts, from GitHub and from a residential IP alike (Oct 16, 2026: 6 of 10 seeded days from GitHub; three in a row here, then fine). A retry a second or two later usually works; 429 means slow down. Keep 2 to 3 requests in flight.
- **One server**: upwell.pfeg 302s to coastwatch.pfeg; coastwatch.noaa.gov has no MUR. More "servers" don't help.
- **"Network is unreachable" that takes the whole connect timeout** (Render, Oct 16, 2026): coastwatch.pfeg.noaa.gov has an A and an AAAA record. On a host without IPv6, urllib3 tries the IPv4 address first; NOAA drops it, so that try waits out the connect timeout, then the IPv6 address fails at once with errno 101, and urllib3 reports only that last error. So each request cost 4 s and the week used the whole 22 s budget ("busy"). `NETSIM=coastwatch.pfeg.noaa.gov=v4drop` reproduces it.
- **404 bodies tell dead from missing**: "Currently unknown datasetID=..." means the dataset is gone; "greater than the axis maximum" / "less than the axis minimum" / "no matching results" means the date isn't in it (`FetchError` kinds dead / missing; missing days of an old week are real gaps and make no retry).
- **Sizes**: one MUR day for the AOI is 4.96 MB as .nc but 0.84 MB gzip-encoded (requests asks for gzip by default), 1 to 2 s from a residential IP. A whole OISST week is ~20 KB. ERDDAP .nc is NetCDF-3, read from memory (`engine="scipy"`); no temp files are left behind any more.
- **Single multi-day NetCDF requests time out** for 7+ days of MUR data. One request per day, a few at a time, is more reliable.
- **Time budgets**: 22 s per week for a reader (about 25 s with processing), 150 s per week for the seeder, 100 s for `/api/precache`.

### ImageOverlay Must Be Non-Interactive
Set `interactive=False` on `dl.ImageOverlay` AND add `pointer-events: none !important` in CSS (`.leaflet-image-layer`). Otherwise the overlay swallows all mouse events, preventing clicks on POI markers underneath.

### ImageOverlay Is Stretched in Web Mercator (the image's rows must be too)
- Leaflet projects an ImageOverlay's corners and stretches the image linearly between them in Web Mercator. Until the relaunch each frame had one image row per grid row, evenly spaced in latitude, so the SST was drawn up to **5.36 km (2.9 nm) north of true at 41.3 N** (mean 3.6 km), while tap readouts (the raw arrays, nearest grid latitude) were right: the color under a tap could be a degree off its own reading. Found by the sprint 2 designer (depth contours on top made it obvious).
- **Fix** (`map/overlay.mercator_rows`): before encoding, output row r is centred where Leaflet draws it and shows the grid row with the nearest centre to that latitude (nearest: exact raw values, land and the AOI mask; no row skipped), rows at most 0.005 deg (0.56 km) tall, so a cell edge lands within 0.28 km of true (max 0.274 km, mean 0.13 km; OISST too). A MUR frame is 1041 rows for 501 grid rows, about 27 KB (190 KB for a week, was 152 KB). Bounds and raw arrays are unchanged.
- **Saved weeks**: frames carry `"frame_format": 2` (`map/overlay.FRAME_FORMAT`). An entry without it (saved before Oct 16, 2026) is redrawn from its own raw arrays when served (about 0.4 s, no NOAA call, so it works on Render) and rewritten in the background (`"write": "upgrade"`); its bounds are recomputed from the grid too (entries from before sprint 1 saved the first/last cell centres instead of the edges). Older code serves the redrawn frames correctly, so a rollback is safe. **Bump `FRAME_FORMAT` whenever the drawing changes** (palette, projection): every saved week then redraws itself on its next view.
- Tests: `tools/test_sst_ui.py` (every image row shows the cell under it; the pixel under 600 random points is the readout's color; the old drawing fails 414 of them), `tools/test_sst_fetch.py` (an old entry is redrawn without NOAA and written back), `tools/smoke_sst.mjs` (in Chrome: the image on its bounds, the legend color under 10 taps vs their readings).
- Sprint 2's client-side engine does the same in the browser: it draws the grid in 16-row strips, each placed by Web Mercator at its cell edges (`tools/test_sstengine.mjs` checks cell centres across a sharp front at zoom 11).

### Interaction Model — Unified Click System
Every tap goes through one clientside callback (`SST.classify`, assets/sst.js) into one selection (`click-pos`: `{kind: "reading" | "poi" | "dump", lat, lng, name}`) or the measure state; `render_selection` draws both for the day on the map. One card at a time; a second tap on it closes it.
- **A spot's circle** (hit-tested in screen pixels, ~16 px for a finger, 9 px for a mouse, so the target is the same at every zoom) → its card: name, temperature, date, position, the week's 7 values there. The old fixed 0.08° radius was 7 px at zoom 7 but 58 px at zoom 10, and hid the water around every spot.
- **Anywhere else**, including next to a spot → the temperature where you tapped. **Inside The Dump** → that point's temperature, named "The Dump" (it used to jump to the box's centre).
- **Measure mode** → A then B, snapping to a spot's circle (not to The Dump's centre).
- POI markers are **visual-only** (`bubblingMouseEvents=True`, no Popup/Tooltip children); the spot list (`sst-pois` store, `map/pois.pois_payload()`) feeds the hit test.
- Readings show tenths ("71.3 °F") since sprint 2 (weeks saved before it read whole degrees until the seeder rebuilds them). Out-of-grid taps read "No data here", not the edge pixel. The card is drawn in the browser from SSTEngine (no server trip).
- Two quick taps are Leaflet's double-tap zoom: closing a card needs a separate tap.

### Performance Notes
- **dcc.Store payload**: ~2 KB since sprint 2 (the week's grid, ~0.6 MB gzip, is fetched by SSTEngine and kept by the browser's HTTP cache for an hour). Before: ~2.5 MB of PNGs.
- **Server-side raw data**: ~25 MB in memory per date window. Falls back to disk cache on miss.
- **Disk cache**: gzip JSON, ~200 KB per date window. Persistent across deploys.
- **Day switching** is a crossfade between two per-day canvases in the browser (SSTEngine); before sprint 2 it swapped pre-rendered PNGs.
- **1x native upsample**: Dropped from 2x to 1x when AOI expanded — reduces payload by ~62% with no visible quality difference at typical zoom levels. The `upsample_visual()` call with factor 1 returns the array unchanged.
- **Coverage** (sprint 2): 37.8 to 44.0 N, 76.0 to 64.8 W, 1121 x 621 at MUR 1 km. Before: Cape May (38.80 N) to Portland, ME (43.80 N), 501 x 617, an AOI polygon.
- **Cache hit path**: disk read + decompress + parse → ~2-5s on Render. No ERDDAP call needed.
- **Closest saved week**: for weeks ending more than 10 days before the newest day, `_saved_nearby()` in app.py takes a saved week within ±3 days of the requested end date before asking NOAA. With pre-cached entries every 7 days, most tuna-season dates hit one, avoiding ERDDAP entirely. The meta says so (`week_match: "closest_saved"`, `requested_end`) and the date box shows the week served. Recent weeks are always fetched exactly (the nearby one is only the fallback). The `data_key` in `sst-store` is the served week's so click-to-read-temp works.
- **Cache miss path** (Oct 16, 2026, this Mac): uncached weeks from 2005, 2009, 2011, 2012, 2014 and 2018 took 4.8 to 6.8 s server-side (fetch 3 to 6 s, processing under 1 s), the newest week 5.6 s; the first fetch after a restart pays ~3 s for the land mask unless the pre-warm loaded it. At worst ~25 s, then the honest failure. Render can fetch ERDDAP again since 2026-10-10 but gets the same 503 bursts; the seeder keeps recent weeks in the cache either way.
- **AOI change invalidates cache**: Disk-cached data has bounding box baked in. After AOI polygon changes, old caches will have wrong bounds — first fetch after change will be a cache miss.
- **Pre-cache strategy**: `/api/precache` endpoint populates disk cache for tuna season dates. Once cached, 2020–2025 Jun–Nov dates load in 2-5s instead of 30-50s. Raw-only cache entries add ~2-3s for on-the-fly PNG rendering on first user load; background thread upgrades to full cache (with PNGs) for instant subsequent loads.
- **GFW tile proxy blocking**: On zoom, Leaflet requests ~48 GFW tiles through the server-side proxy, each taking ~1s (GFW API latency). Fix: `--threads 16` allows concurrent I/O (tile fetches release the GIL), and server-side tile cache (`_gfw_tile_cache`) makes repeat requests instant. `updateWhenZooming=False` + `updateWhenIdle=True` + `keepBuffer=4` further reduce tile requests. Since Oct 16, 2026 at most 6 GFW calls run at once (4 more tiles wait up to 3 s, the rest get 503 "busy" and the page retries them), so a zoom burst or a GFW outage leaves threads for everything else; a first zoom to a new area takes a few seconds longer than with 16 tiles at once. Subsequent zooms to the same area are instant from cache.

## Environment Variables
| Variable | Required | Purpose |
|----------|----------|---------|
| `GFW_API_TOKEN` | No | Global Fishing Watch API token (JWT). Enables fishing activity overlay. Without it, layer degrades gracefully (transparent tiles). |
| `SST_CACHE_DIR` | Yes (Render) | Cache directory path. Set to `/var/data/cache` on Render (persistent disk mount). Default `./cache` for local dev. |
| `CACHE_UPLOAD_TOKEN` | Yes (Render) | Shared secret (`X-Upload-Token`) for `POST /api/cache/upload`, `POST /api/currents/upload`, `GET /api/cache/wanted`, `GET /api/precache` and `GET /api/debug/threads`; also a GitHub repo secret for the seed and currents workflows. Unset → those endpoints are disabled (403). |
| `CURRENTS_DATA_DIR` | No | Override for the /currents data dir. Default `$SST_CACHE_DIR/currents` (→ `/var/data/cache/currents` on Render). |
| `CATCH_DATA_DIR` | Yes (Render) | Directory holding the catch CSVs (`/var/data/cache` on Render). Default: the repo's `data/`. |
| `CATCHES_ACCESS_KEY` | Yes (Render) | Access key for `/catches` (`?key=…`). Unset on Render → page closed. |
| `CATCHES_UPLOAD_TOKEN` | No | Secret for `POST /api/catches/upload` (catch sync — not automated yet; CSVs are uploaded by hand). |
| `LABS_HOST` | No | `labs.gotoneapp.com` → page loads on `sst.gotoneapp.com` redirect there (set only once that domain works). Unset → the old host serves the SST map at `/`. |
| `LABS_STATS_KEY` | Yes (Render) | Key for the private stats (`/labs/stats?key=…`, `/api/labs/stats?key=…`). Unset on Render → 404. |
| `LABS_STATS_DIR` | No | Override for the stats directory (SQLite + salt). Default `$SST_CACHE_DIR/stats` (→ `/var/data/cache/stats` on Render). Tests point it at a temp dir. |
| `PORT` | Render only | Set automatically by Render for gunicorn binding. |
| `SST_NOAA_READERS` | No | Request threads that may wait on NOAA at once (default 4); the next reader gets the honest answer at once. Keep well under gunicorn's `--threads`. |
| `NOAA_MAX_CALLS` / `GFW_MAX_CALLS` | No | Outside calls in flight per upstream (defaults 10 and 6; `data/outbound.py`). |
| `SLOW_REQUEST_S` | No | A request running longer than this (default 60 s) is logged with its stack by the watchdog. |
| `REQUEST_THREADS` | No | gunicorn's `--threads` (default 16), for the watchdog's "all request threads busy" dump. |
| `GFW_API_BASE` | No | Tests only: another base URL for the GFW API (a local fake). Default `https://gateway.api.globalfishingwatch.org`. |
| `SST_CACHE_MAX_MB` | No | Disk budget for the SST cache files, in MB. Default: 70% of the disk `SST_CACHE_DIR` is on (Render's 1 GB disk: 700 MB). Past it, eviction removes superseded old entries, then the least recently viewed weeks. |
