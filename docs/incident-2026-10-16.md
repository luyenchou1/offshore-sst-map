### 4. Root cause
All routes share one process and 16 request threads. Every request whose handler waits on an outside server holds one
of them; when 16 are held, gunicorn's gthread worker keeps accepting and queues every new request (static ones too)
behind them, while its main loop keeps heartbeating, so there is no WORKER TIMEOUT and no traceback. Sprint 1 left
three ways for request threads to wait on an outside server for minutes or without end:

1. **The GFW tile proxy holds a process-wide lock across GFW's generate-png call** (new in sprint 1: before, each tile
   called it without a lock, in parallel) **and remembers no failure**. When GFW is failing, a screenful of tiles goes
   through the lock one at a time at 15-30 s each (2 IPv4 addresses x 15 s on a host without IPv6), each holding a
   request thread; with HTTP/2 at Render's edge a page asks for 12-20 tiles at once, and every further tile request
   (the test harness kept requesting /api/gfw tiles) joins the queue. When GFW is slow rather than down, requests'
   `timeout=15` (a per-read timeout) never fires and the queue never drains. Tile fetch failures are not logged at all.
2. **NOAA reads have no real deadline**: `http_get` checks the budget only between 64 KiB chunks and
   `iter_content(64 KiB)` waits until a whole chunk has arrived, so a slow NOAA answer holds the thread far past its
   budget. `latest_time(block=True)` runs it on request threads (`fetch_sst_data`, `get_sst_multiday`,
   `fetch_oisst`). When NOAA is unreachable, nothing fails fast either: every uncached week costs a request thread the
   whole 22 s budget, however many readers ask at once, and the per-week lock makes the others wait up to 25 s.
3. **The land mask download runs under `_LAND_LOCK`** with only per-read timeouts, and waiters have no timeout.

The production trigger: NOAA unreachable from Render (reproduced exactly with `v4drop`) made uncached weeks cost 22 s
each, then the test toggled Fishing activity and kept requesting GFW tiles; those requests piled up behind
`_gfw_style_lock`, which took all 16 threads. Nothing was logged for 11 minutes, which matches GFW being slow rather
than refusing, or the other silent waits (tile fetches, gunicorn's reads of idle connections, below). Exactly what GFW
did from Render at 20:52 can't be told from the log. Every variant that matches the symptoms goes through items 1-3,
and each one is fixed below.

Contributing: **gunicorn >= 24 hands each accepted connection straight to a pool thread**, which blocks reading the
request with no timeout (23.0.0 waited in its poller until the socket was readable). 16 connections that send nothing
freeze the worker. Render's proxy normally sends the request with the connection, but requirements.txt allows any
gunicorn >= 21.2, so the version in production is whatever pip resolved at the build (26.2.0 today). Also, requests
whose client already gave up (curl timed out) are still executed when a thread frees up, so a backlog keeps the
server busy long after the load stops.

### 5. The fix (branch sst1-fix)
- **`data/outbound.py` (new)**: every outside call (NOAA, GFW, Natural Earth) goes through an `Upstream`. The call runs
  on the upstream's own threads and the caller waits only until its deadline (`future.result(timeout)`), so the request
  thread is free at the deadline whatever happens (DNS, several addresses, TLS, a drip). The body is read with
  `raw.read1()`, checking the deadline after each piece and capping the socket timeout by the time left, so the
  upstream's own thread ends at the deadline too. A full pool refuses at once ("busy"), and only a few callers may wait
  for a slot. The circuit breaker opens after connect failures (unreachable, refused, no DNS, connect timeout; for GFW
  also timeouts, 3 in a row), refuses every call for 60 s, then lets one probe through. Breaker trips and recoveries
  are logged.
- **NOAA** (`data/erddap.py`): `http_get` goes through the NOAA upstream (10 calls in flight). The new kind
  `unreachable` is never retried; MUR days stop at the first one and OISST (same server) isn't tried, giving reason
  `network`. Connect timeout 3 s (was 4). The newest-day lookup is single-flight (one request per dataset; other callers
  wait for it, bounded) and the fetch callback no longer waits for it. Fixed the `_latest_refreshing` bookkeeping.
- **Loading a week** (`app._load_week`): first everything that needs no NOAA (saved copy, closest saved week, a failure
  in the last minute). Then NOAA only if its breaker is closed and one of `SST_NOAA_READERS` (4) reader slots is free;
  otherwise the honest answer comes at once, with the nearest saved weeks and the week queued for the seeder. A wait for
  another visitor's fetch of the same week that runs out answers "busy" instead of starting a second fetch. Fixed: a
  remembered failure's minute restarted every time someone asked, so a popular week was never retried. New honest
  message for "network": "We can't reach NOAA's data server right now, so ... didn't load."
- **GFW tile proxy**: no lock held across a call. One generate-png per range (6 s max); up to 4 tiles wait for it
  (4 s max) and the rest get 503 "busy"; a failed range is remembered for 60 s. Calls go through the GFW upstream:
  6 at once, 4 more tiles wait up to 3 s, the rest get 503 "busy" (no image body, `Retry-After: 1`, no-store). A GFW
  failure gives an empty 200 PNG with no-store (not cached for a day) and a rate-limited log line (failures used to
  be silent). `assets/sst.js` retries 503 tiles (up to 4 times, 0.5-1.2 s first), so a zoom's 30-50 tiles still all
  arrive.
- **Land mask** (`data/geo.py`): the download is bounded (40 s), runs in its own thread with no lock held, callers wait
  with a timeout (5 s in the app, only once per load), and a week built without the mask is served but not saved.
  Precache waits up to 60 s for it and never saves a week without it.
- **Precache**: `_call_with_timeout` (`shutdown(wait=False, cancel_futures=True)`); the old `with ThreadPoolExecutor`
  waited for the fetch on exit, so the 120 s limit never applied.
- **Diagnostics**: faulthandler on SIGUSR1 (chained to gunicorn's handler only when one exists; chaining to the default
  action would kill a plain `python app.py`), `GET /api/debug/threads` (token-locked: requests running with ages,
  upstream states, reader slots, locks, recent failures, every thread's stack), and a watchdog that logs any request
  over 60 s with its stack and dumps every thread when all 16 are that slow.

### 7. Not fixed here
- gunicorn >= 24's gthread worker still reads each new connection on a pool thread with no timeout (gunicorn's design,
  not the app's): 16 connections that send nothing would still freeze it. Render's proxy sends the request with the
  connection, so this isn't known to have happened. Pin a tested version and run the load test before moving.
- Seen while testing: on some /sst loads right after a server boot, assets/sst.js never defines `window.SST`. It
  happens with the original sprint-1 file too (4 of 12 loads with 4 pages at once), so it predates this fix. Not fixed
  here; filed as a follow-up. On such a page the GFW 503 retry isn't installed either.
- NOAA is still unreachable from Render (as of Oct 16), so cache misses there answer "We can't reach NOAA's data
  server right now" and depend on the seeder (`seed-sst-cache.yml`).
